# Marin app builder

## Purpose

Build small, focused MarinOS micro-apps using Marin's existing standards and implementation, not invented-on-the-spot patterns.

This skill is the synthesis point, not a fourth source of truth:

> `marin-digital-standards` (standards define) → `marin-ui` (UI implements) → `marin-app-template` (template assembles) → **this skill** (how an AI agent uses all three together) → the Marin product.

Don't restate any of those repos' content here beyond what's needed to sequence a build — consult them directly, and update this skill only if the sequencing itself changes. In particular, don't reconstruct the project structure or UI system from these docs when a working instance of both already exists in `marin-app-template` — start there instead.

## Before building, consult

- [`marin-app-template`](https://github.com/marincountygov/marin-app-template) — the starting point for every build. Its `index.html`, `assets/`, and vendored `marin-ui` bundle already encode the required shell, branding, menu behavior, font loading, theme handling, and accessibility baseline. Its `docs/development.md` covers customizing it and updating the vendored bundle.
- [`marin-ui/docs/architecture.md`](https://github.com/marincountygov/marin-ui/blob/main/docs/architecture.md) — frontend stack, file structure, JavaScript/storage rules, for anything the template doesn't already show.
- [`marin-ui/docs/components.md`](https://github.com/marincountygov/marin-ui/blob/main/docs/components.md) — the shared component library to draw from before writing new markup or CSS.
- [`marin-ui/docs/accessibility-implementation.md`](https://github.com/marincountygov/marin-ui/blob/main/docs/accessibility-implementation.md) and [`marin-digital-standards/accessibility`](https://github.com/marincountygov/marin-digital-standards/tree/main/accessibility) — WCAG 2.2 AA, for anything beyond what the template's shell already satisfies.
- [`marin-digital-standards/content-design`](https://github.com/marincountygov/marin-digital-standards/tree/main/content-design) — interface copy, heading case, plain language, descriptions.
- [`marin-digital-standards/brand`](https://github.com/marincountygov/marin-digital-standards/tree/main/brand) — only if a build needs a brand decision the template's already-configured tokens and shell don't cover.
- [`marin-digital-standards/product-design`](https://github.com/marincountygov/marin-digital-standards/tree/main/product-design) — only if the app is a resident-facing public service rather than an internal tool; the build workflow below assumes the internal-tool case by default.
- [`marin-digital-standards/security`](https://github.com/marincountygov/marin-digital-standards/tree/main/security) and [`marin-os/schemas/security.schema.json`](https://github.com/marincountygov/marin-os/blob/main/schemas/security.schema.json) — only if the app isn't a typical internal staff tool (see `security/profiles.md` for `public-web`/`public-api`/`authenticated`/`custom`); the template's starter `security.json` already covers the default `internal` case.

Do not invent a new visual pattern, component, or copy convention when an approved one already covers the requirement — that's the single most common way a generated app drifts from the rest of MarinOS.

## Build workflow

1. If the owner has a finished Marin Spec (`SPEC.md`, written with the `marin-spec` skill or the Marin Spec app), build from it: read all of it, including Non-goals and Open questions, map each requirement to the template, and check each acceptance criterion before finishing. Ask only about blocking questions. The spec says what to build; the standards and the template decide how it looks and behaves.
2. Confirm scope: a small internal tool, review app, data-cleanup utility, form workflow, or dashboard (the default case this skill covers), or a resident-facing public service (also apply `marin-digital-standards/product-design`).
3. Start the project from `marin-app-template` (use it as the GitHub template, or copy its structure) rather than assembling `index.html`, the shell, branding, menu behavior, or font loading from scratch. Its vendored `marin-ui` bundle already provides Pico.css, `app-brand.css`, `app-shell.js`, local Open Sans for body/UI text, and local Jost for heading/display text. Don't introduce React, Vue, Svelte, Angular, Next.js, Tailwind, Bootstrap, npm build steps, frontend routing frameworks, Google Fonts, Adobe Fonts, jsDelivr, unpkg, cdnjs, or other runtime static-asset CDNs unless explicitly requested and justified — the template deliberately has none.
4. Replace the `APP_NAME`, `APP_DESCRIPTION`, `APP_OWNER`, and `APP_REPO` placeholders in `index.html`, `README.md`, and `security.json` (the `exceptions[].owner` and `review.owner` fields) with the real product name, one-sentence plain-language description, owner, and GitHub repo slug.
5. Add only application-specific code: replace the starter `#start` section in `index.html` with the real workflow, add app-specific state and behavior to `assets/app.js`, and add app-specific styling to `assets/app.css` only after confirming an existing `marin-ui` component or token doesn't already cover it. Do not add app-level `@import` font rules, Google Fonts links, external CDN CSS/JS includes, or ad hoc `font-family` stacks; inherit the template's `--app-font-body` and heading tokens unless a standard explicitly says otherwise. Leave `#about` and `#updates` in place — every app keeps About and Updates in `#app-nav`; `#start` already covers the "Home" case as the default view's own task tab, so no separate Home link is needed unless the workflow grows a distinct landing view later (see `marin-ui/docs/components.md`, "Standard app nav"). The default view must stay immediately functional — keep info/how-to/context content out of it and in About instead. That means no intro or explainer paragraph, no visible page heading that just repeats the app name or purpose (use a `visually-hidden` `<h2>` to keep heading order), and no help text under a search box. Reference apps like `marin-mentions` have none.
6. Use `localStorage` only for small preferences; `IndexedDB` via Dexie for real records or larger structured data; include JSON export/import for any meaningful local data.
7. Build the added content to WCAG 2.2 Level AA — the template's shell already meets this baseline, so focus here on whatever's new: form fields, dynamic content, custom controls. See `marin-ui/docs/accessibility-implementation.md` for the exact patterns.
8. Pick the app's icon before registering it: choose the closest stock Lucide icon to what the app does (see `marin-ui/docs/components.md`, "App icon," and `marin-ui/vendor/icons/lucide/` for what's already vendored — add the one new SVG file there if the app needs an icon not yet in that folder, sourced from lucide.dev, ISC-licensed). Use that single icon in all three places: the template's placeholder header `.app-icon`, the placeholder favicon `data:image/svg+xml` URI (same rounded-square/gold-stroke wrapper, just the app-specific path data), and the `catalog.json` `icon` field below. Never leave the template's generic four-square placeholder in a shipped app. Copy the icon's path data from the Lucide package (for example `lucide/dist/esm/icons/<name>.js`) rather than writing it from memory, and use the icon the owner names if they name one.
9. If the app is meant to be part of MarinOS (not a one-off/private tool), register it: add an entry to [`marin-os/catalog.json`](https://github.com/marincountygov/marin-os) (id, name, type, url, description, audience, status, owner, `icon` — the same icon from step 8) and the matching directory card to `marin-os/index.html`, then run `node scripts/check-catalog-sync.js` in that repo. `status` is one of `alpha`/`beta`/`live` (see `marin-os`'s own `#status` page for what each means) — a freshly scaffolded app starts at `alpha`, matching `marin-app-template/marin.yml`'s own default. That's the entire registration step — every other MarinOS app's banner menu picks up the new entry automatically at runtime; don't hand-edit any other app's repo. Also create a `marin.yml` manifest in the new app's repo (see `marin-app-template/marin.yml` for the fields and an existing app's for a filled-out example) and a short `AGENTS.md` pointing at `marin-ui`, `marin-digital-standards`, and `marin-skills`.
10. Confirm the security setup the template already ships with actually fits this app rather than leaving it on autopilot: is `internal` (the template's default) still the right profile, or does this app need `public-web`/`public-api`/`authenticated`/`custom` per `marin-digital-standards/security/profiles.md`? Does `data.acceptsUserSubmittedContent`/`collectsSensitiveData`/`externalDataSources` in `security.json` still reflect what this app actually does, now that step 5's real workflow exists? Run `node marin-os/scripts/validate-security.js security.json` and `node marin-os/scripts/check-security.js .` (paths relative to a local `marin-os` checkout) before shipping. Route a deeper pass — CSP specifics, a genuine exception, anything beyond confirming the defaults still fit — to `security-review`.

The skill should not independently recreate the project structure or UI system — if a build needs something the template and `marin-ui` don't provide, that's a signal to extend those repos, not to invent a one-off pattern inside a single product.

## Data-browsing apps (list, calendar, stats)

When the app lets people browse, filter, and summarize records, copy the interaction model of the reference app `marin-mentions` instead of designing a new one. Read its `index.html`, `assets/app.css`, and `assets/app.js` first, and re-read the real source before reproducing a pattern — do not approximate it from memory. The one thing not to copy from its markup is the filter column: it is drawn from `filters.json` (see the Filter column bullets below).

- **Tabs:** a `role="tablist"` of `.mm-tab` buttons with `aria-selected`, `aria-controls`, roving `tabindex`, and arrow/Home/End keys, inside a bordered `.mm-tab-row` above the results. Switching tabs never resets filters. Keep view state in the URL query string. A Map tab, when records have locations, goes between Calendar and Stats; build and review it with the `map-views` skill.
- **Read the rules before you add or change anything in a list view (filter, sort, layout, cards, columns, the line above the results).** Read the sections "Filter column", "Results header" and "Cards" of `marin-ui/docs/components.md` and the real source of the reference app (`marin-mentions`, `marin-reach`), not only the shell's `docs/components.md`. A `filters.json` that passes `audit-filter-column.py` is valid; it is not proof the design follows the rules. The audit checks the file's shape, not what the control is for. Do not add a control, a group, a label or a piece of text the rules do not describe; if the rules do not cover something the app needs, ask the owner or leave it out, and say so in the report.
- **Filter column (only when the app has a list people search or filter):** an app with no such list has no filter column, no `filters.json` and no `.search-layout`; do not add one to match other apps. When the app does need one, never write the column by hand (no sidebar, toggle, search box, Reset button, filter-group markup or placeholder). The shell (App Shell 2.0.0 and later) draws it from one file. Write `filters.json` next to the page, following `vendor/marinos/filter-panel.schema.json` (the "Filter column" section of `marin-ui/docs/components.md` and the shell's `docs/components.md` own the reference), then put one empty `<div class="search-side" data-filter-column="filters.json" data-filter-name="things"></div>` inside a `.search-layout`, beside a `.search-results` area. `python3 vendor/marinos/audit-filter-column.py . --fail` (already in the starter's `scripts/check.sh`) lists a hand-written column and any file that breaks the schema.
- **What the schema decides, so the app does not:** the title is the one word "Filter" and the Reset icon sits beside it; Search is the first field, labelled "Search", with no placeholder and never in the toolbar (leave `search` out of the file when a short list needs none); every group shows its name as a plural noun ("Departments", "Monitors", "Sources"), never "Custodian department" or "Filter by source"; a group with nothing chosen reads "All" and the plural noun ("All departments", never "Any status"). Group types are `checkbox` (collapsed, or always showing with `"collapsed": false`), `nested-checkbox` (`groupBy`, with `parentField` for a division under its department), `radio`, `select` and `date-range`. Choices come from the app's own data file (`options.from`, with `order: "data"` to keep the file's order) or, for a live feed or worked-out values, from the app (`options: {"app": true}` then `setOptions`). Do not copy spacing, the toggle, the narrow-screen behavior, the scrolling or the keyboard and focus handling into the app: the shell owns them and tests them. A page opened from a catalog (a course, a note, a detail page) has no filter column; keep the column in the page template that only the catalog draws.
- **The app's part:** listen for `marin-filter-change` (`detail.state` holds the search and every group's choice, `detail.source` is `reset` after Reset), do the matching in the app's one selectors module, then call `setResults(count)` on the column so it announces the count once and offers Reset filters when nothing matches (put `data-filter-results` on the element that holds that message; with the results line, mark that line and pass the node `marinResultsLine` makes as the second argument, so it stays the only count). Keep supplying counts with `setCounts(groupId, {value: n})` and group totals with `setGroupCounts`. Never disable an option. The column keeps the search and choices in the address; the app writes only its own parameters (view, sort, tab) and leaves the rest alone. `marin-jobs` (a live feed) and `marin-software` are the simplest examples; `marin-mentions` (nested groups, a Time choice, two columns), `marin-reach` (a date range, facets with counts) and `marin-learn` (a column drawn from a template) show the rest.
- **Filters are multi-select by default.** Write a group as `checkbox` (or `nested-checkbox`) so people can combine choices: OR within a group, AND across groups. Use `select` or `radio` only when the choices exclude each other because something confines them (a time range, a year, a version, a budget book). Never a drop-down for themes, departments, categories or statuses.
- **A choice of one belongs in the filter column too, when the choices exclude each other.** Which year, version or measure the cards, stats and charts show (such as Recommended or Adopted) is a filter, not a toolbar control or a dropdown among the sort and view buttons. List it in `filters.json` as a `select` (or `radio`) group with a `default` (`"latest"` for the newest value, or a value), above the multi-select filters. One is always chosen, Reset puts it back, and the toolbar keeps only sort, view and Copy/Download. Change the page when the choice is made. A single option needs no control.
- **A list stays a directory; configuring and comparing belongs to the compare and reports tool.** The filter column holds only what narrows which records show (Search, the kinds of record, dates, statuses). Do not put a column picker, a measure picker, a layout setting or any other way to configure what a table holds in the list view, in the filter column or in a toolbar menu. A table in the list has a fixed set of columns. Choosing measures, setting up a comparison and building a report is one tool (the shell's `docs/reports-plan.md`: a report is a list of sections, and a comparison is a section type). A group with choices ticked on load opens expanded and reads "(N selected)", the shell's wording, which cannot be edited, so use one only where the default is part of the design (area types with tracts off, a short `"collapsed": false` list). The toolbar keeps sort, layout (cards or table), Copy link, Copy, Download and Fullscreen.
- **Reset:** the column's Reset deselects every filter, clears the search, restores a choice of one to its default and collapses every group. The app does the rest in its `marin-filter-change` handler when `detail.source` is `reset`: back to the first tab (never stays on Stats, Data or Notes), and, for a choice that opens another page (a book, a year), go to the latest. Sort and view stay as they are.
- **Line above the results:** one line that counts what the list shows with the name its cards use (`32 places`), then ` / ` and only the choices that narrow it beyond how the page opened (`32 places / Census tract`, `1 place / “bel”`), regular weight, muted choices, never "Showing:", "All ...", totals or a breakdown. It is `.mm-results-summary` with `data-filter-results`, made by `marinResultsLine({ count, filters })` and passed to the column's `setResults(count, node)`, under the tab row and above the toolbar; it is the only count (no "N of M" line, no filter chips, no buttons for it). The standard is "Results header" in `marin-ui/docs/components.md`; check it against `marin-mentions` before finishing.
- **Where the source goes:** a list page (cards or a table of many things) shows no source line. The source sits on the page of one thing, and an app with a Data tab gives the dataset, its release and each measure's source table there. Copies and downloads still carry the source.
- **Layout (cards or table):** a list of named things opens on cards (the name a link, one or two figures as lines of text) and offers a table. Cards and table are icon-only buttons in one `.action-group` of the toolbar (`aria-pressed`; Lucide `layout-grid` and `table`), after the sort group. The sort group shows on cards and hides on the table, which sorts from its headings (a first click on a heading is ascending; a card sort button starts at its natural order, and pressing the pressed one reverses it and changes its label). The toolbar order is sort, layout, then Copy link, Copy, Download and, last, Fullscreen in a group of its own. Copy link, the two menus and the status line sit in a `.doc-actions` that is a direct child of the `.action-toolbar`, never inside an `.action-group`: a menu inside a group gets a second border and looks bigger than its neighbors. Fullscreen is its own `.action-group` so it has space around it. Every table and every page of a thing (a place, a department) has Copy link, Copy (Text, HTML, Markdown) and Download (Text, HTML, Markdown, JSON, CSV) in this order. The layout and the sort are kept in the address next to the filter column's own parameters. When the app writes the address, keep `location.hash`: the shell's tabs use it, and dropping it sends a person to the first tab.
- **Sort:** icon buttons in the first `.action-group` of the toolbar, as in Reach (`#sort-group`, `aria-pressed` on the active one, `aria-label` and `title` naming each, e.g. "Name, A to Z", "Value, high to low"), never a select in the sidebar. Offer a sort for each thing people compare (name, amount, date), and hide the group on Stats. Keep the sort in the URL.
- **Order of service areas and agencies:** service areas, departments, divisions and other County bodies run A to Z by name in every list, table, card grid, chart and filter group, and a list of them opens on "Name, A to Z" (standard in `marin-digital-standards/product-design/interaction-design.md`). A ranking chart ("Largest departments") may order by amount; a page that reproduces a printed book keeps its order.
- **Stats and filters:** Stats shows only what is relevant to the filter; a whole-book overview is hidden while any search or filter choice is active (the year does not count).
- **Forms:** a form carries only form functions (fields, labels, help text, its buttons). Do not add icons, illustrations, or other embellishments to it.
- **Action buttons** (shell `.action-toolbar` of `.action-group` clusters, `.action-button` with Lucide icons, App Shell 1.15.0 and later; only a button that submits a form is the solid blue or dark one): on the list, Copy, Link, CSV, and RSS; on Stats, Copy and All PNG plus Link, with a PNG button under each chart. Copy and CSV act on the checked listings, or on everything shown when none are checked. Copy writes rich text with the `execCommand` technique used in Mentions, with the visible textarea fallback. Copied text has no emoji, no "Showing:" prefix, and no date after the app name in its heading. Every listing also gets its own Copy button (the shell's `.copy-button` with the check-mark feedback), and a Link button beside it when the listing can be reached by address (`.copy-button` with the Lucide `link` shape, copying a link that opens the app filtered to that listing). Show each action's result ("Copied 3 engagements to clipboard.") in a `role="status"` line directly below the button row, or below the listing's own button, not only in the global live region. RSS is a link (`role="button"`) that answers the Space key, says "opens in a new tab" in its `aria-label`, and is hidden, with no explanation text, when no static feed matches the active filters (a search, a date range, another filter, or several projects). Generate the feeds in the data build. Icon-only controls (per-listing Copy, Show on map with the Lucide `map-pin`, Get directions with `signpost`) use the shell's `.copy-button` with an `aria-label` and sit in that order in the card's action row; a directions control is a link with `role="button"` that opens in a new tab, says so in its name, and answers the Space key; a control that sits with the toolbar buttons uses `.action-button`, icon only, named by `aria-label` and `title`. A pair pressed often or on touch (Previous and Next) uses `.action-group--spaced` (App Shell 1.16.0 and later): separate buttons, 44 pixels square, with a gap. A text button the owner asks for ("Learn more") keeps its word and adds an icon after it. A lone `.action-button` (outside an `.action-group`) has a visible border (App Shell 1.20.0 and later); never override it per app. Use a short text label only when icons alone would be ambiguous, such as "Copy text" next to "Copy HTML". Every Copy button is one icon button with a menu of Text, HTML and Markdown, in that order (App Shell 1.22.0 and later: `marinContentFormats` reads a page, `marinFormatMenus` wires the menu to your own strings, and `data-formats-for` wires a page with no script); never a Copy button that offers only one format. A button that copies the page address is **Copy link** with the `link` icon (`data-action="share"` keeps the shell's behavior), never a share icon or the word "Share". Page actions come in one order: Copy link, Copy, Download, then Print and anything the app adds; Copy and Download are icon-only (a menu button is named "Copy, choose a format" and reports `aria-expanded`). Previous and Next carry an arrow on the outside (left of Previous, right of Next), `aria-hidden`.
- **Actions above tables:** the buttons for a table (Copy, Download, the choice of layout) are one row above the table, not below it. A Download with more than one file type is a menu with an item for each (CSV, JSON). A choice between layouts of the same content is icon-only `.action-button`s with `aria-pressed`, each named for what it shows. An accordion has a border; one inside another is a plain line that opens. A key number's value is the link and its words sit at the base of the card as plain text.
- **Search box and results page:** a search box outside the filter column is the filter column's `.search-input-field` (label above, the same field as Marin Mentions), not Pico's pill input. Enter goes to a page of results (`search.html?q=`) that lists every result with where it sits; a result opens its page on what was found.
- **Search results:** a box that lists results shows the count line above them (`3 results`, then `matching “x”`), not "N found."; the list is left aligned with no bullets.
- **A page opened from a search:** it is about the thing found (its name is the heading, a list of its own facts as links, then its own figure, the buttons, the table of its rows; no "Showing:" line, since it is a page and not a filtered list). A larger thing's totals are not shown on the page of a part of it. There is no row of links back to the results. Results are grouped by kind.
- **Action button order and sharing:** layout choice, Copy, Copy link, Download, Fullscreen. The address holds the layout so a shared link opens on it. Pages of the same kind have headings built alike (name, then code as a link).
- **Charts:** the same four buttons as a table, in the same order (Copy, Copy link, Download, Fullscreen); a Dashboard's section headings are the size of other pages' section headings.
- **Stats tables:** a table on a Stats tab is a table block with the same buttons as every table (its CSV read from the table, since it follows the filters); in a toolbar Fullscreen is the last button.
- **Fullscreen:** every table's row of action buttons ends with a Fullscreen button (Lucide `maximize`, as the slides of Marin Learn have; `data-fullscreen-target` names what opens, the table with its buttons above it). The action buttons stay in the fullscreen. It opens as a dialog: focus stays inside (Tab goes round), a live region announces it, Escape closes it, and focus returns to the button. A chart is selected and copied like a table. A page of figures that follow a filter has a "Showing:" line above them that says what they are.
- **Tables:** a table people copy from selects like a spreadsheet (column letters, row numbers, a corner, a cell; drag or Shift for a range, Ctrl or Command to add one) with no sticky columns, and its headings stay in view with their borders (separate borders) and has a Copy menu above it (Text, CSV) for the selection; bold column headings; columns sort (`.sort-button`, `aria-sort`); pressing a cell marks its row and column and outlines the cell; the table scrolls inside its own region with its heading and first column kept in view.
- **Buttons everywhere** (App Shell 1.17.0 and later; standard in `marin-digital-standards/product-design/interaction-design.md`): never use Pico's `secondary`, `outline` or `contrast` classes, `link-button`, or a bare `<button>`. A utility action is `.action-button` with `data-icon="name"` (the shell draws the Lucide icon) and `aria-label` plus `title`; keep words only on the one main action, dialog buttons, and anything without a familiar icon. The one main action of a screen is the only solid button (`.primary` or `type="submit"`). Tabs are `.tab-list` and `.tab-button`, filter chips `.chip-button`, sortable headers `.sort-button`, dialog buttons `.dialog-actions`, and a deleting action adds `.is-danger`. Run `python3 ../marin-app-shell/scripts/audit-buttons.py .` before finishing; it must list nothing.
- **Step flows** (report builders, wizards, guided workflows; standard in `marin-digital-standards/product-design/interaction-design.md`): the Next button that moves on is the one solid button of the screen, a real `<button class="primary" data-icon-end="arrow-right">` that keeps its words and names the next step in lowercase ("Next: coverage"). Previous sits to its left as a quiet icon-only `<button class="action-button" data-icon="arrow-left" aria-label="Previous: details" title="Previous: details">`, the same as Copy, Print and Download, 44 px square; the first step has no Previous and the last has no Next. Number the steps "1. Name" with `aria-current="step"` on the current one and the solid accent highlight. No circled numbers. A short flow inside one feature (the `marin-mentions` report builder) shows them as a row of `.tab-button` items above the content. An app whose whole workflow is the steps (`marin-spec`) puts them in the shell's collapsible left column: a `nav` list inside `.search-sidebar`, `data-filter-toggle` with `data-filter-label="Steps"`, and a visible current-step line ("Step 2 of 6: Analyze") as the first child of `.search-results`, so the narrow-screen toggle has a row to sit beside. App Shell 1.23.0 and later sizes the arrow; on an older release, size it in the app's CSS. Read `marin-mentions/assets/reports/ui.js` and `marin-spec` before reproducing it.
- **Order:** show the newest date first in the list, CSV, and copied text unless the owner asks otherwise.
- **Listings:** an `.app-card.mm-card` with the checkbox column on the left and a Select all checkbox above the list. Make checkboxes 24 px square (WCAG 2.5.8) instead of Pico's smaller default. In a detail dialog, put the Close button below the card, not beside it. Name per-listing controls (checkbox, Copy) with the title plus date and time so repeated titles stay distinct. Show the title first, then labeled fields in one `dl`, with the same label/value format for each (including Date), and end with Status.
- **Calendar:** a Day, Week or Month range select with Previous and Next buttons (`marin-reach`; no separate Today button, because today is marked in the grid), a month or week grid (a real `<table>` with header cells), plus an agenda list that replaces the grid on narrow screens and serves the Day range. Show every event on a day. Name each event button with its time, title, and status; mark status with outline style and text, not color alone (canceled is struck through), and print a short legend. Show today's date with a bold outlined circle, never an underline. Selecting an event opens the same detail as the list in a native `<dialog>`; give the dialog its `aria-labelledby` only when its title exists, and put focus on the title.
- **Stats:** KPI tiles (`.mm-stats-kpi`) and Chart.js charts on canvas in `.app-card`s, in the same blue (`#0777cf`) as Mentions. Not HTML tables. Each canvas needs `role="img"`, a text summary in `aria-label`, and a data table for screen readers inside a `visually-hidden` wrapper `<div>` (the class does not clip a `<table>` on its own). Set the chart library's default text and grid colors from the page's computed colors so dark mode stays readable, rebuild charts when the color scheme changes, and give PNG exports the card background. Reuse the vendored `chart.min.js` and `CHART_LICENSE.md` from Mentions, keep the script `defer`red, and add the notice to `THIRD_PARTY_NOTICES.md`. Create charts only while their panel is visible, but fill the screen-reader tables and text summaries on every render so a table is never empty. Every drawn chart on any page, not only on a Stats tab, has its own Copy and Download bar above it, left-aligned and built like a table's (`.doc-actions` with the shell's Copy and Download menus): Copy as an image or as text, Download as a PNG saved with `marinDownload` as `{page} - {chart title} - {date}.png` on the card's own background so light text stays readable. Tables and charts show their buttons the same way. A page with several charts also has, in a `Chart actions` group in the toolbar, Copy (every chart as an image plus a text summary, through `marinCopyRich`) and a download-all-PNG button (`marinDownload`, one file per chart staggered by 150 ms); on a Stats tab these replace the Copy and Download menus and the Link button stays. In `marin-docs` the bar is written with the chart (`chartActions` in `scripts/page-actions.js`) and wired once in `organization/page-data.js`.
- **Feedback button:** the shell (1.11.0 and later) hides the floating Feedback button while the footer is on screen; do not add your own floating control without the same behavior.
- **Test banner:** an app or section that is a design test with unreviewed data shows the shared `.app-test-banner` under the header, with the text "TEST: This is a design test. Data shown has not been fully reviewed and is for test use only." (exact; see "Test banner" in `marin-ui/docs/components.md`). Switch it on in `marin.yml` with `project.test: true` for the whole app or `project.test_sections: folder/` (comma-separated folders) for sections, and have the build write it; never add it by hand to single pages.
- **Cards:** the name (a link to the page of the thing) 1.25rem and bold, a line or two of text 1rem, a small line 0.875rem, both regular; no badges except a status, which is the shell's status badge (`.app-status`, `data-status` open/done/warning/danger), a `button.app-status` where it filters. A card shows only what identifies the thing and its one or two figures; everything else is on the thing's own page, in a `.facts` list. Names are cased as a department's are (`display-name.js`).
- **Content:** no intro text, no explainer under the search box, and no "view" in button or link labels; see "Review checklist" below. Write no explanatory text of your own (what a label means, how a figure is worked out, why two numbers differ, what a source does not give) unless the owner asks for it. Show the source's own labels and values; if a meaning is not stated in the source, leave it out rather than infer it. A note the owner asks for comes from the data (a JSON file), not from the code.

Show every state: loading, error with retry, no results, and an empty calendar month. The loading message is always "Loading {app name}…" (see "Wording for messages" below). Use `marin-skills/data-visualization-skill` for chart choices and accessible alternatives.

## Wording for messages

- **Loading:** any "still loading" text, in the page or in a section, reads `Loading {app name}…` (for example `Loading Marin Reach…`), including the text announced to screen readers. Do not name the data being loaded ("Loading engagement records…") and do not write a bare "Loading…". Marin App Shell 1.12.2 and later builds its own sections' messages this way and exposes `window.MarinAppShell.loadingMessage()` for an app's own text.
- **No ancillary text:** never add counts or tallies of what is hidden ("25 more.", "14 programs.") under a heading or list; a link to the full list is enough. A short list of cards shows whole rows only (`docs-grid--3`, 3 or 6 cards), never an orphan card on the last row.
- **Interface text:** no intro paragraph or page heading on the main page, no help text under a search box, and no "view" in button or link labels (see the data-browsing section).
- **Never "view":** no app uses "view" in a button or link label, whether or not it browses data. A card with one destination makes its title the link, with no separate button. Card grids use the shell's `.app-card` look (as the MarinOS home page does), not a custom card style. Put badges after the description.
- **No breadcrumb where something else already shows the place.** Tabs (Marin Budget) and the left navigation of a document set (Marin Docs) already do, so those pages have none. Add a breadcrumb only when a page sits two levels deep with no tabs or navigation to show where you are, such as Marin Learn's course viewer (`Catalog / Course name`, links for every step but the last), or when asked. Even then, the way back is the trail, never a "Back to catalog" button.

## Long pages with sections

- **On this page:** a page with several sections gets a table of contents named "On this page": a `nav.docs-toc` with `aria-label="On this page"` and links to the sections' `id`s, in the right-hand column on wide screens and above the content on narrow ones. The shell marks the section being read with `aria-current="location"` (bold, normal text color) as the reader scrolls, with no app JavaScript. The list is a bordered box with a ruled heading and stacked links, and the page content is a plain bordered box with no shadow, the same as the Marin Learn notes reader (Marin UI 1.31.0 and later, App Shell 1.20.0 and later); never add your own `.toc` styles or a shadow on `.content`. If the app builds the page with JavaScript, call `window.marinOnThisPage(nav)` after the sections and the list are in the page. Only list sections that exist, and use the same words as the headings. See `marin-ui/docs/components.md`, "On this page".
- **Section boxes:** when each section is its own block of content, give it a box: the card look (border, radius, surface background) without the shadow.
- **Secondary cards:** a group of smaller, supporting cards, such as a Help section under a main list of cards, uses a quieter card: smaller icon, title, and description. Keep the primary card's structure (icon, title as the link, one short description) and the same description rules.

- **Marin Learn content:** a course's Note, deck, and quiz follow the `marin-learn-content` skill. The deck and quiz are built with `scripts/build_note_deck.mjs` and `scripts/build_note_quiz.mjs`, never written by hand.

## Sets of documents (guides, regulations, procedures)

When the app holds documents that belong together (the pages of a guide, the regulations of a manual, a collection of procedures), copy `marin-docs` instead of designing the navigation. The standards are in `marin-ui/docs/components.md`: "Document set outline", "Document set landing page" and "Search results that show where the words are". Read them and the reference code (`marin-docs/scripts/doc-nav.js`, `doc-pager.js`, `build-pmrs.js`, `home-search.js`, `doc-search.js`, `doc-highlight.js`) before writing anything.

- **Left navigation:** one navigation for every kind of document, with three levels (the set, its groups, its documents), the current document marked with `aria-current="page"`, and a search box under the set's title. Build it from the data the set already has (a guide's `groups`, a manual's order, a procedure's department) with one function, as plain HTML. Never write it by hand into a page, and never put the sections of the current document in it: they stay in "On this page" on the right. A long set opens only the group that holds the current document.
- **Previous and next** at the foot of each document, in the set's own order, from the same data.
- **List page:** one card for each group, listing its documents as links, with a search box above that looks through the whole set. Only what the data holds: no written summaries or explanation. The cards are the navigation there, so the left navigation is not drawn.
- **Search that reads text:** a search of the text of documents shows, under each result, a line of the text with the matched words marked, and marks the same words on the page that opens (the words travel in `sessionStorage`, never in the address). The text is in one file for each set, read only after a person starts to search; the small list that finds names does not carry it. A box in a sidebar lists names only.
- **A glossary for each set that defines terms:** one glossary page for the set (not one shared across sets, because the same word means different things in different sets), built from the set's own `DefinedTerm` data: terms A to Z, each definition in the data's words with a link to the section that defines it, a "Reference" group in the left navigation, a card on the list page, and the terms in the set's search. It has no previous and next links and no Citation. Do not link a term inside the text unless the data says where each use is. See `marin-ui/docs/components.md`, "Document set glossary", and `marin-docs/scripts/build-pmrs.js`.
- **Listed documents only:** a document left off the lists is left off the navigation, the pager, the cards and every search file. Read the structured list, not the folder.
- **Below the home page** every page has the same shell as the home page (header with About and Updates, footer, Feedback) and no breadcrumb.
- **Copy, share and download** above the title of a document, as the shell provides them (`data-formats-for` on the article); a document with structured data also offers it as JSON, and a document people quote has Citation in its Copy menu and, at the end of each numbered section, the same Copy link and Copy menu (Text, HTML, Markdown, Citation) scoped to that section, with its own status line (see `marin-ui/docs/components.md`, "Citing a document"). **Every copy and download function is an item in the Copy or Download menu, never a separate button**: a new function is a new menu item, and a part of a page gets the same group scoped to it. Do not hide a copy function only in a menu at the top, and do not add a stand-alone "Copy citation" or "Copy text" button.

## Apps that produce a report or document

`marin-mentions` Reports is the working example (`assets/reports/`).

- **Store the report as data, render it as a document.** Keep a versioned object (`schemaVersion`) as the source of truth and render it with one function for the on-screen report, Copy for Word, copying a part, and any download. Never build report markup in a second place, and never store generated HTML as the report.
- **Keep a snapshot of each source item** (headline, publication, date, link) so a saved report still opens after the item leaves the live data.
- **Word-friendly copy:** semantic HTML only (h1 to h3, p, ul, table with `th scope`), tables with `border` and `cellpadding` attributes (Word draws gridlines from attributes, not CSS), absolute links, no classes, scripts, inline styles, or layout CSS. Pass that HTML and a plain-text version to the shell's `marinCopyRich(text, html)` (App Shell 1.21.0 and later). Never copy a rendered element (a hidden `contenteditable` you select and `execCommand("copy")`): the browser adds the page's fonts, sizes and bold weights as inline styles, and a CMS turns a bold heading into `<strong>`. Show a visible text box when copying fails, and show the result ("Report copied. Paste it into Word.") in a status line next to the button. Tests prove the markup (no `style=`, no `<strong>`); a person must paste into Word on Windows and Mac, and into the CMS, and record the result.
- **Copy, download, file reading and upload** (App Shell 1.21.0 and later; standard in `marin-digital-standards/product-design/text-characters-copy-and-upload.md`, patterns in the shell's `docs/components.md`): use the shell helpers and do not write your own. `marinCopyRich` and `marinCopyText` for the clipboard; `marinDownload({content, name})` to save a file (a CSV gets a byte-order mark so Excel reads accents and apostrophes); `marinReadText(file)` to read a file (UTF-8, then Windows-1252, never "�", never `file.text()` or `readAsText`); `marinCleanText(value)` for output that goes to a CMS, a URL or a CSV (opt-in: text that is only shown keeps its curly quotes); `marinUpload({...})` for the upload screen (a card headed **Upload**, "Drag and drop a .csv/.xlsx file anywhere on this page, or use the browse button.", a **Browse files** button, drop anywhere, the standard error messages). Several formats are one Copy button and one Download button, each opening a `.menu` that lists Text, HTML, then Markdown. Say nothing about a character fix that went fine. Run `python3 vendor/marinos/audit-shared-helpers.py .` before finishing; it must list nothing.
- **Dates:** decide days in the organization's time zone (Pacific for County reports), not UTC, and keep dates as ISO strings. A post at 5 pm Pacific is the next day in UTC.
- **Imported files are untrusted:** validate the version and structure, trim and length-limit text, escape everything when rendering, and keep only http, https, and mailto links. Give plain-language errors for a bad file.
- **Drafts:** a draft saved in the browser needs a note that it stays on that device, a way to download the report as a file, and a flush on `pagehide` so a quick reload does not lose the last edit.
- **Curation, not guessing:** do not infer classifications (for example whether coverage resulted from a news release). Let people place and order items with buttons, never drag-only.
- **Links from aggregators:** items found through Google News carry a Google link, not the publisher's page. Make the link editable.

## Apps built from a spreadsheet, CSV, or JSON file

When the data starts as a spreadsheet or a structured file, keep the file as the editable source and generate the data the app reads. `marin-reach` is the working example; it started from a CSV and now builds from a JSON-LD graph (`data/source/marin-reach-engagements.json`).

- **Pipeline:** one script (`scripts/build_data.py`, standard library only) reads the file in `data/source/`, trims values, normalizes dates and times, builds a stable id, validates against a schema in `data/schema/`, and writes the JSON the page loads. It fails with the row number (CSV) or the record id (JSON) on bad data, on unknown or missing headers or required fields, and on `U+FFFD` replacement characters. Commit the generated files so the site needs no build.
- **JSON-LD source:** read `@graph`, treat only the record type you need (for example `Event`) as records, and resolve `{"@id": ...}` references to named entities, failing on any that do not resolve. Ignore properties the model does not carry. Keep the written local time and date without time-zone conversion. Keep the derived record flat so the UI and selectors do not change; add a structured `place` (kind, address, `geo`) only for what a map needs. Validate coordinates as numbers in range and together, and never guess them (see `map-views`).
- **`--check` mode:** the same script verifies the committed outputs are current and fails when they are stale or when extra generated files exist. Run it from `scripts/check.sh`.
- **Aliases are data:** display names such as "CDA" to "Community Development Agency" live in `data/aliases.json`, never in UI code. Keep the source value next to any renamed value.
- **Never merge uncertain values.** Write abbreviation-like values with no alias, and values that differ only by case or punctuation, to a generated `data/ambiguities.md` for the data owner.
- **Multi-value fields** split on `;` only, because commas appear inside names.
- **Feeds:** if the app offers RSS, generate static feeds in the same script.
- **One filtering path:** put every filter, search, grouping, and count in one pure module (`assets/selectors.js`) used by every tab, so counts always agree. The UI reads and writes the URL query string and holds no canonical data.
- **Document it:** a data dictionary, the normalization rules, and a decision log of resolved and deferred items, so later agents do not re-decide them.

## Testing a MarinOS app

- Unit-test the pure modules: Python `unittest` for the converter and Node's built-in `node --test` for the selectors. No test dependencies.
- Run Playwright from a virtual environment outside the repo when it is not installed (`python3 -m venv`, `pip install playwright`, `playwright install chromium`), and add an axe-core scan of the key views in light and dark as a check, not a conformance result. Search is debounced and the shell fades elements with CSS transitions, so wait for the result before asserting.
- Add one Playwright workflow test (Python) that serves the repo under a project-site path such as `/<repo>/`, fixes the clock, and runs light and dark. It should cover filters, tab switching with state kept, the calendar, dialogs, stats, copy and download buttons, empty and error states, keyboard reach, and narrow screens with no horizontal scroll.
- After changing the shell, Marin UI, or any shared stylesheet, compare computed styles (colors, borders, shadows) for every element on the same pages before and after, in light and dark mode, and explain every difference. This is how a refresh is proved to change nothing, and it found two bugs that token-based contrast checks could not.
- Under the static CSP, use Playwright locator waits, not string-based `wait_for_function`, which needs `unsafe-eval`.
- `marin-app-template` 2.0.3 and later has a working `tests/browser_smoke.py` for the starter and a CSP that allows the shell's Accessibility score and Tech data requests. In a real app, replace its assertions with the app's own workflow test (keep the file if `tests/browser_security.py` imports helpers from it). An app made from an older template may have the old failing test and a CSP missing `marin-os/data/lighthouse.json` and `marin-os/data/tech.json`; add those two URLs to `security.json` `csp.directives.connect-src`, run `python3 scripts/sync-security-meta.py --write`, and note them in `data.externalDataSources`.
- When an app is served from `localhost`, the shell reads that score and Tech data from a local MarinOS server (`http://localhost:8935`), which the app's CSP blocks on purpose. Ignore that one blocked-request console message in tests and check those two sections on the deployed app.

## Boundaries

This skill builds and reviews the *whole* app shell — it doesn't replace a focused review. For a deep pass on one dimension, use the specific skill instead: `accessibility-review` for WCAG conformance beyond this checklist, `design-review` for County visual-identity compliance, `plain-language-review` or `inclusive-language-review` for content, `digital-service-design` for a resident-facing service's task flow, `security-review` for CSP specifics, a genuine security exception, or anything beyond confirming the template's security defaults still fit.

This skill doesn't own project scaffolding or the UI system — those belong to `marin-app-template` and `marin-ui` respectively. If a build repeatedly needs something neither provides, that's a signal to extend the template or `marin-ui`, not to work around the gap inside this skill or a single product.

- **The line above results:** the count of the things the list shows, with the name the cards use, and nothing else (a list of vendors says `1,648 vendors`, not the contracts); then ` / ` and only the choices that narrow it (never "All ...", never the figure choices, no default choice, no breakdown, no totals); regular weight with the choices muted; 1rem above and 0.5rem below, set once on `.mm-results-summary`; no "Showing:", no Reset link; made by `marinResultsLine` (`shared/results-line.js`); always above a list, never on a page about one thing. Stylesheets that import stylesheets carry a stamp on every `@import` (`scripts/stamp-css.js`) so a changed style is read at once.
