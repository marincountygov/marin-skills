# Marin app builder

## Purpose

Build small, focused MarinOS micro-apps using Marin's existing standards and implementation, not invented-on-the-spot patterns.

This skill is the synthesis point, not a fourth source of truth:

> `marin-digital-standards` (standards define) → `marin-ui` (UI implements) → `marin-app-template` (template assembles) → **this skill** (how an AI agent uses all three together) → the Marin product.

Don't restate any of those repos' content here beyond what's needed to sequence a build — consult them directly, and update this skill only if the sequencing itself changes. In particular, don't reconstruct the project structure or UI system from these docs when a working instance of both already exists in `marin-app-template` — start there instead.

## Before building, consult

- [`marin-app-template`](https://github.com/marincountygov/marin-app-template) — the starting point for every build. Its `index.html`, `assets/`, and vendored `marin-ui` bundle already encode the required shell, branding, menu behavior, font loading, theme handling, and accessibility baseline. Its `docs/development.md` covers customizing it and updating the vendored bundle.
- [`marin-ui/docs/architecture.md`](https://github.com/marincountygov/marin-ui/blob/main/docs/architecture.md) — frontend stack, file structure, JavaScript/storage rules, for anything the template doesn't already show.
- [`marin-ui/docs/components.md`](https://github.com/marincountygov/marin-ui/blob/main/docs/components.md) — the shared component library to draw from before writing new markup or CSS.
- [`marin-ui/docs/accessibility-implementation.md`](https://github.com/marincountygov/marin-ui/blob/main/docs/accessibility-implementation.md) and [`marin-digital-standards/accessibility`](https://github.com/marincountygov/marin-digital-standards/tree/main/accessibility) — WCAG 2.2 AA, for anything beyond what the template's shell already satisfies.
- [`marin-digital-standards/content-design`](https://github.com/marincountygov/marin-digital-standards/tree/main/content-design) — interface copy, heading case, plain language, descriptions.
- [`marin-digital-standards/brand`](https://github.com/marincountygov/marin-digital-standards/tree/main/brand) — only if a build needs a brand decision the template's already-configured tokens and shell don't cover.
- [`marin-digital-standards/product-design`](https://github.com/marincountygov/marin-digital-standards/tree/main/product-design) — only if the app is a resident-facing public service rather than an internal tool; the build workflow below assumes the internal-tool case by default.
- [`marin-digital-standards/security`](https://github.com/marincountygov/marin-digital-standards/tree/main/security) and [`marin-os/schemas/security.schema.json`](https://github.com/marincountygov/marin-os/blob/main/schemas/security.schema.json) — only if the app isn't a typical internal staff tool (see `security/profiles.md` for `public-web`/`public-api`/`authenticated`/`custom`); the template's starter `security.json` already covers the default `internal` case.

Do not invent a new visual pattern, component, or copy convention when an approved one already covers the requirement — that's the single most common way a generated app drifts from the rest of MarinOS.

## Build workflow

1. Confirm scope: a small internal tool, review app, data-cleanup utility, form workflow, or dashboard (the default case this skill covers), or a resident-facing public service (also apply `marin-digital-standards/product-design`).
2. Start the project from `marin-app-template` (use it as the GitHub template, or copy its structure) rather than assembling `index.html`, the shell, branding, menu behavior, or font loading from scratch. Its vendored `marin-ui` bundle already provides Pico.css, `app-brand.css`, `app-shell.js`, local Open Sans for body/UI text, and local Jost for heading/display text. Don't introduce React, Vue, Svelte, Angular, Next.js, Tailwind, Bootstrap, npm build steps, frontend routing frameworks, Google Fonts, Adobe Fonts, jsDelivr, unpkg, cdnjs, or other runtime static-asset CDNs unless explicitly requested and justified — the template deliberately has none.
3. Replace the `APP_NAME`, `APP_DESCRIPTION`, `APP_OWNER`, and `APP_REPO` placeholders in `index.html`, `README.md`, and `security.json` (the `exceptions[].owner` and `review.owner` fields) with the real product name, one-sentence plain-language description, owner, and GitHub repo slug.
4. Add only application-specific code: replace the starter `#start` section in `index.html` with the real workflow, add app-specific state and behavior to `assets/app.js`, and add app-specific styling to `assets/app.css` only after confirming an existing `marin-ui` component or token doesn't already cover it. Do not add app-level `@import` font rules, Google Fonts links, external CDN CSS/JS includes, or ad hoc `font-family` stacks; inherit the template's `--app-font-body` and heading tokens unless a standard explicitly says otherwise. Leave `#about` and `#updates` in place — every app keeps About and Updates in `#app-nav`; `#start` already covers the "Home" case as the default view's own task tab, so no separate Home link is needed unless the workflow grows a distinct landing view later (see `marin-ui/docs/components.md`, "Standard app nav"). The default view must stay immediately functional — keep info/how-to/context content out of it and in About instead. That means no intro or explainer paragraph, no visible page heading that just repeats the app name or purpose (use a `visually-hidden` `<h2>` to keep heading order), and no help text under a search box. Reference apps like `marin-mentions` have none.
5. Use `localStorage` only for small preferences; `IndexedDB` via Dexie for real records or larger structured data; include JSON export/import for any meaningful local data.
6. Build the added content to WCAG 2.2 Level AA — the template's shell already meets this baseline, so focus here on whatever's new: form fields, dynamic content, custom controls. See `marin-ui/docs/accessibility-implementation.md` for the exact patterns.
7. Pick the app's icon before registering it: choose the closest stock Lucide icon to what the app does (see `marin-ui/docs/components.md`, "App icon," and `marin-ui/vendor/icons/lucide/` for what's already vendored — add the one new SVG file there if the app needs an icon not yet in that folder, sourced from lucide.dev, ISC-licensed). Use that single icon in all three places: the template's placeholder header `.app-icon`, the placeholder favicon `data:image/svg+xml` URI (same rounded-square/gold-stroke wrapper, just the app-specific path data), and the `catalog.json` `icon` field below. Never leave the template's generic four-square placeholder in a shipped app. Copy the icon's path data from the Lucide package (for example `lucide/dist/esm/icons/<name>.js`) rather than writing it from memory, and use the icon the owner names if they name one.
8. If the app is meant to be part of MarinOS (not a one-off/private tool), register it: add an entry to [`marin-os/catalog.json`](https://github.com/marincountygov/marin-os) (id, name, type, url, description, audience, status, owner, `icon` — the same icon from step 7) and the matching directory card to `marin-os/index.html`, then run `node scripts/check-catalog-sync.js` in that repo. `status` is one of `alpha`/`beta`/`live` (see `marin-os`'s own `#status` page for what each means) — a freshly scaffolded app starts at `alpha`, matching `marin-app-template/marin.yml`'s own default. That's the entire registration step — every other MarinOS app's banner menu picks up the new entry automatically at runtime; don't hand-edit any other app's repo. Also create a `marin.yml` manifest in the new app's repo (see `marin-app-template/marin.yml` for the fields and an existing app's for a filled-out example) and a short `AGENTS.md` pointing at `marin-ui`, `marin-digital-standards`, and `marin-skills`.
9. Confirm the security setup the template already ships with actually fits this app rather than leaving it on autopilot: is `internal` (the template's default) still the right profile, or does this app need `public-web`/`public-api`/`authenticated`/`custom` per `marin-digital-standards/security/profiles.md`? Does `data.acceptsUserSubmittedContent`/`collectsSensitiveData`/`externalDataSources` in `security.json` still reflect what this app actually does, now that step 4's real workflow exists? Run `node marin-os/scripts/validate-security.js security.json` and `node marin-os/scripts/check-security.js .` (paths relative to a local `marin-os` checkout) before shipping. Route a deeper pass — CSP specifics, a genuine exception, anything beyond confirming the defaults still fit — to `security-review`.

The skill should not independently recreate the project structure or UI system — if a build needs something the template and `marin-ui` don't provide, that's a signal to extend those repos, not to invent a one-off pattern inside a single product.

## Data-browsing apps (list, calendar, stats)

When the app lets people browse, filter, and summarize records, copy the interaction model of the reference app `marin-mentions` instead of designing a new one. Read its `index.html`, `assets/app.css`, and `assets/app.js` first, and re-read the real source before reproducing a pattern — do not approximate it from memory.

- **Tabs:** a `role="tablist"` of `.mm-tab` buttons with `aria-selected`, `aria-controls`, roving `tabindex`, and arrow/Home/End keys, inside a bordered `.mm-tab-row` above the results. Switching tabs never resets filters. Keep view state in the URL query string. A Map tab, when records have locations, goes between Calendar and Stats; build and review it with the `map-views` skill.
- **Layout:** `.search-layout` with a sticky `.search-sidebar` on the left and `.search-results` on the right; the sidebar collapses behind a Filters toggle (not a modal) on narrow screens, and can be hidden on wide screens too. Use the shell's collapsible filter panel (Marin UI 1.28.0 and later, App Shell 1.14.0 and later): inside a `.search-layout`, put an empty `<button type="button" class="filter-toggle" data-filter-toggle="name" aria-controls="panel-id">` at the top of a `.search-side` column, above the `.search-sidebar` panel, and set `<body data-app-id>`. The shell draws the Lucide `panel-right-open` and `panel-left-open` icons, runs the toggle (open on wide screens and closed up to 850 px, a wide-screen choice remembered in `localStorage`, `aria-expanded`, the hidden panel out of the tab order, focus kept on the button) and names it "Filters" plus ", N active" from `data-filter-active`. The app only keeps `data-filter-active` current and listens for `marin-filters-change` to resize anything sized by the results (a Leaflet map's `invalidateSize()`); hiding the panel must never change a filter. Do not copy the toggle CSS or script into the app. `marin-reach` and `marin-mentions` use it.
- **Sidebar** (the "Filter column" section of `marin-ui/docs/components.md` owns the markup and spacing; Marin UI 1.30.0 and later carries the CSS, and until an app installs it the app mirrors the `marin-mentions` styles exactly): a title row with "Filter" plus the plural thing ("Filter Mentions", "Filter software") and the Reset icon button beside it (`.search-panel-header`, `.search-panel-title`, `.action-button` with `data-icon="rotate-ccw"`), then Search, then the other controls, then the filter groups in the order the owner specifies. Search is the first field, a normal `.search-input-field`: label "Search" above, a full-width rounded-rectangle box that matches the selects (never Pico's pill, never `role="search"`, never in the toolbar), and a placeholder short enough to fit the 248 px column ("Search systems…", not "Name, vendor, purpose…"). Name each filter with a plural noun ("Departments", "Monitors", "Sources"), not "Custodian department" or "Filter by source". Make each filter a collapsed `<details class="mm-facet-group">` inside a `.search-facet-group` fieldset with a `<legend>`, holding multi-select checkboxes in `.search-facet-list` with `.search-facet-count` counts; show "(N selected)" or "N selected" in the summary and open the group on load when it holds a selection. Do not add your own spacing: rows are 0.45rem apart, groups and fields 1.5rem, checkboxes 24 px. Keep a short date range as plain inputs. Combine within a filter with OR and across filters with AND. Include every field the owner lists as a filter, such as Status. Before finishing, open the app next to `marin-mentions` and compare the filter column: the title row, the search box, the group spacing and the collapsed groups must look the same.
- **Summary line:** a bold "Showing: ... (N items — breakdown)" line describing the active filters, as in Mentions. Do not use filter chips or "Showing N of M" text, and do not use buttons for it.
- **Forms:** a form carries only form functions (fields, labels, help text, its buttons). Do not add icons, illustrations, or other embellishments to it.
- **Action buttons** (shell `.action-toolbar` of `.action-group` clusters, `.action-button` with Lucide icons, App Shell 1.15.0 and later; only a button that submits a form is the solid blue or dark one): on the list, Copy, Link, CSV, and RSS; on Stats, Copy and All PNG plus Link, with a PNG button under each chart. Copy and CSV act on the checked listings, or on everything shown when none are checked. Copy writes rich text with the `execCommand` technique used in Mentions, with the visible textarea fallback. Copied text has no emoji, no "Showing:" prefix, and no date after the app name in its heading. Every listing also gets its own Copy button (the shell's `.copy-button` with the check-mark feedback), and a Link button beside it when the listing can be reached by address (`.copy-button` with the Lucide `link` shape, copying a link that opens the app filtered to that listing). Show each action's result ("Copied 3 engagements to clipboard.") in a `role="status"` line directly below the button row, or below the listing's own button, not only in the global live region. RSS is a link (`role="button"`) that answers the Space key, says "opens in a new tab" in its `aria-label`, and is hidden, with no explanation text, when no static feed matches the active filters (a search, a date range, another filter, or several projects). Generate the feeds in the data build. Icon-only controls (per-listing Copy, Show on map with the Lucide `map-pin`, Get directions with `signpost`) use the shell's `.copy-button` with an `aria-label` and sit in that order in the card's action row; a directions control is a link with `role="button"` that opens in a new tab, says so in its name, and answers the Space key; a control that sits with the toolbar buttons uses `.action-button`, icon only, named by `aria-label` and `title`. A pair pressed often or on touch (Previous and Next) uses `.action-group--spaced` (App Shell 1.16.0 and later): separate buttons, 44 pixels square, with a gap. A text button the owner asks for ("Learn more") keeps its word and adds an icon after it. A lone `.action-button` (outside an `.action-group`) has a visible border (App Shell 1.20.0 and later); never override it per app. Use a short text label only when icons alone would be ambiguous, such as "Copy text" next to "Copy HTML".
- **Buttons everywhere** (App Shell 1.17.0 and later; standard in `marin-digital-standards/product-design/interaction-design.md`): never use Pico's `secondary`, `outline` or `contrast` classes, `link-button`, or a bare `<button>`. A utility action is `.action-button` with `data-icon="name"` (the shell draws the Lucide icon) and `aria-label` plus `title`; keep words only on the one main action, dialog buttons, and anything without a familiar icon. The one main action of a screen is the only solid button (`.primary` or `type="submit"`). Tabs are `.tab-list` and `.tab-button`, filter chips `.chip-button`, sortable headers `.sort-button`, dialog buttons `.dialog-actions`, and a deleting action adds `.is-danger`. Run `python3 ../marin-app-shell/scripts/audit-buttons.py .` before finishing; it must list nothing.
- **Order:** show the newest date first in the list, CSV, and copied text unless the owner asks otherwise.
- **Listings:** an `.app-card.mm-card` with the checkbox column on the left and a Select all checkbox above the list. Make checkboxes 24 px square (WCAG 2.5.8) instead of Pico's smaller default. In a detail dialog, put the Close button below the card, not beside it. Name per-listing controls (checkbox, Copy) with the title plus date and time so repeated titles stay distinct. Show the title first, then labeled fields in one `dl`, with the same label/value format for each (including Date), and end with Status.
- **Calendar:** a Day, Week or Month range select with Previous and Next buttons (`marin-reach`; no separate Today button, because today is marked in the grid), a month or week grid (a real `<table>` with header cells), plus an agenda list that replaces the grid on narrow screens and serves the Day range. Show every event on a day. Name each event button with its time, title, and status; mark status with outline style and text, not color alone (canceled is struck through), and print a short legend. Show today's date with a bold outlined circle, never an underline. Selecting an event opens the same detail as the list in a native `<dialog>`; give the dialog its `aria-labelledby` only when its title exists, and put focus on the title.
- **Stats:** KPI tiles (`.mm-stats-kpi`) and Chart.js charts on canvas in `.app-card`s, in the same blue (`#0777cf`) as Mentions. Not HTML tables. Each canvas needs `role="img"`, a text summary in `aria-label`, and a data table for screen readers inside a `visually-hidden` wrapper `<div>` (the class does not clip a `<table>` on its own). Set the chart library's default text and grid colors from the page's computed colors so dark mode stays readable, rebuild charts when the color scheme changes, and give PNG exports the card background. Reuse the vendored `chart.min.js` and `CHART_LICENSE.md` from Mentions, keep the script `defer`red, and add the notice to `THIRD_PARTY_NOTICES.md`. Create charts only while their panel is visible, but fill the screen-reader tables and text summaries on every render so a table is never empty.
- **Feedback button:** the shell (1.11.0 and later) hides the floating Feedback button while the footer is on screen; do not add your own floating control without the same behavior.
- **Content:** no intro text, no explainer under the search box, and no "view" in button or link labels; see "Review checklist" below.

Show every state: loading, error with retry, no results, and an empty calendar month. The loading message is always "Loading {app name}…" (see "Wording for messages" below). Use `marin-skills/data-visualization-skill` for chart choices and accessible alternatives.

## Wording for messages

- **Loading:** any "still loading" text, in the page or in a section, reads `Loading {app name}…` (for example `Loading Marin Reach…`), including the text announced to screen readers. Do not name the data being loaded ("Loading engagement records…") and do not write a bare "Loading…". Marin App Shell 1.12.2 and later builds its own sections' messages this way and exposes `window.MarinAppShell.loadingMessage()` for an app's own text.
- **Interface text:** no intro paragraph or page heading on the main page, no help text under a search box, and no "view" in button or link labels (see the data-browsing section).
- **Never "view":** no app uses "view" in a button or link label, whether or not it browses data. A card with one destination makes its title the link, with no separate button. Card grids use the shell's `.app-card` look (as the MarinOS home page does), not a custom card style. Put badges after the description.
- **Breadcrumbs, not back buttons:** show the way back as a trail such as `Catalog / Course name`, with links for every step but the last. Do not write "Back to catalog" buttons.

## Long pages with sections

- **On this page:** a page with several sections gets a table of contents named "On this page": a `nav.docs-toc` with `aria-label="On this page"` and links to the sections' `id`s, in the right-hand column on wide screens and above the content on narrow ones. The shell marks the section being read with `aria-current="location"` (bold, normal text color) as the reader scrolls, with no app JavaScript. The list is a bordered box with a ruled heading and stacked links, and the page content is a plain bordered box with no shadow, the same as the Marin Learn notes reader (Marin UI 1.31.0 and later, App Shell 1.20.0 and later); never add your own `.toc` styles or a shadow on `.content`. If the app builds the page with JavaScript, call `window.marinOnThisPage(nav)` after the sections and the list are in the page. Only list sections that exist, and use the same words as the headings. See `marin-ui/docs/components.md`, "On this page".
- **Section boxes:** when each section is its own block of content, give it a box: the card look (border, radius, surface background) without the shadow.
- **Secondary cards:** a group of smaller, supporting cards, such as a Help section under a main list of cards, uses a quieter card: smaller icon, title, and description. Keep the primary card's structure (icon, title as the link, one short description) and the same description rules.

- **Marin Learn content:** a course's Note, deck, and quiz follow the `marin-learn-content` skill. The deck and quiz are built with `scripts/build_note_deck.mjs` and `scripts/build_note_quiz.mjs`, never written by hand.

## Apps that produce a report or document

`marin-mentions` Reports is the working example (`assets/reports/`).

- **Store the report as data, render it as a document.** Keep a versioned object (`schemaVersion`) as the source of truth and render it with one function for the on-screen report, Copy for Word, copying a part, and any download. Never build report markup in a second place, and never store generated HTML as the report.
- **Keep a snapshot of each source item** (headline, publication, date, link) so a saved report still opens after the item leaves the live data.
- **Word-friendly copy:** semantic HTML only (h1 to h3, p, ul, table with `th scope`), tables with `border` and `cellpadding` attributes (Word draws gridlines from attributes, not CSS), absolute links, no classes, scripts, inline styles, or layout CSS. Pass that HTML and a plain-text version to the shell's `marinCopyRich(text, html)` (App Shell 1.21.0 and later). Never copy a rendered element (a hidden `contenteditable` you select and `execCommand("copy")`): the browser adds the page's fonts, sizes and bold weights as inline styles, and a CMS turns a bold heading into `<strong>`. Show a visible text box when copying fails, and show the result ("Report copied. Paste it into Word.") in a status line next to the button. Tests prove the markup (no `style=`, no `<strong>`); a person must paste into Word on Windows and Mac, and into the CMS, and record the result.
- **Copy, download, file reading and upload** (App Shell 1.21.0 and later; standard in `marin-digital-standards/product-design/text-characters-copy-and-upload.md`, patterns in the shell's `docs/components.md`): use the shell helpers and do not write your own. `marinCopyRich` and `marinCopyText` for the clipboard; `marinDownload({content, name})` to save a file (a CSV gets a byte-order mark so Excel reads accents and apostrophes); `marinReadText(file)` to read a file (UTF-8, then Windows-1252, never "�", never `file.text()` or `readAsText`); `marinCleanText(value)` for output that goes to a CMS, a URL or a CSV (opt-in: text that is only shown keeps its curly quotes); `marinUpload({...})` for the upload screen (a card headed **Upload**, "Drag and drop a .csv/.xlsx file anywhere on this page, or use the browse button.", a **Browse files** button, drop anywhere, the standard error messages). Several formats are one Copy button and one Download button, each opening a `.menu` that lists Text, HTML, then Markdown. Say nothing about a character fix that went fine. Run `python3 vendor/marinos/audit-shared-helpers.py .` before finishing; it must list nothing.
- **Dates:** decide days in the organization's time zone (Pacific for County reports), not UTC, and keep dates as ISO strings. A post at 5 pm Pacific is the next day in UTC.
- **Imported files are untrusted:** validate the version and structure, trim and length-limit text, escape everything when rendering, and keep only http, https, and mailto links. Give plain-language errors for a bad file.
- **Drafts:** a draft saved in the browser needs a note that it stays on that device, a way to download the report as a file, and a flush on `pagehide` so a quick reload does not lose the last edit.
- **Curation, not guessing:** do not infer classifications (for example whether coverage resulted from a news release). Let people place and order items with buttons, never drag-only.
- **Links from aggregators:** items found through Google News carry a Google link, not the publisher's page. Make the link editable.

## Apps built from a spreadsheet, CSV, or JSON file

When the data starts as a spreadsheet or a structured file, keep the file as the editable source and generate the data the app reads. `marin-reach` is the working example; it started from a CSV and now builds from a JSON-LD graph (`data/source/marin-reach-engagements.json`).

- **Pipeline:** one script (`scripts/build_data.py`, standard library only) reads the file in `data/source/`, trims values, normalizes dates and times, builds a stable id, validates against a schema in `data/schema/`, and writes the JSON the page loads. It fails with the row number (CSV) or the record id (JSON) on bad data, on unknown or missing headers or required fields, and on `U+FFFD` replacement characters. Commit the generated files so the site needs no build.
- **JSON-LD source:** read `@graph`, treat only the record type you need (for example `Event`) as records, and resolve `{"@id": ...}` references to named entities, failing on any that do not resolve. Ignore properties the model does not carry. Keep the written local time and date without time-zone conversion. Keep the derived record flat so the UI and selectors do not change; add a structured `place` (kind, address, `geo`) only for what a map needs. Validate coordinates as numbers in range and together, and never guess them (see `map-views`).
- **`--check` mode:** the same script verifies the committed outputs are current and fails when they are stale or when extra generated files exist. Run it from `scripts/check.sh`.
- **Aliases are data:** display names such as "CDA" to "Community Development Agency" live in `data/aliases.json`, never in UI code. Keep the source value next to any renamed value.
- **Never merge uncertain values.** Write abbreviation-like values with no alias, and values that differ only by case or punctuation, to a generated `data/ambiguities.md` for the data owner.
- **Multi-value fields** split on `;` only, because commas appear inside names.
- **Feeds:** if the app offers RSS, generate static feeds in the same script.
- **One filtering path:** put every filter, search, grouping, and count in one pure module (`assets/selectors.js`) used by every tab, so counts always agree. The UI reads and writes the URL query string and holds no canonical data.
- **Document it:** a data dictionary, the normalization rules, and a decision log of resolved and deferred items, so later agents do not re-decide them.

## Testing a MarinOS app

- Unit-test the pure modules: Python `unittest` for the converter and Node's built-in `node --test` for the selectors. No test dependencies.
- Run Playwright from a virtual environment outside the repo when it is not installed (`python3 -m venv`, `pip install playwright`, `playwright install chromium`), and add an axe-core scan of the key views in light and dark as a check, not a conformance result. Search is debounced and the shell fades elements with CSS transitions, so wait for the result before asserting.
- Add one Playwright workflow test (Python) that serves the repo under a project-site path such as `/<repo>/`, fixes the clock, and runs light and dark. It should cover filters, tab switching with state kept, the calendar, dialogs, stats, copy and download buttons, empty and error states, keyboard reach, and narrow screens with no horizontal scroll.
- After changing the shell, Marin UI, or any shared stylesheet, compare computed styles (colors, borders, shadows) for every element on the same pages before and after, in light and dark mode, and explain every difference. This is how a refresh is proved to change nothing, and it found two bugs that token-based contrast checks could not.
- Under the static CSP, use Playwright locator waits, not string-based `wait_for_function`, which needs `unsafe-eval`.
- `marin-app-template` 2.0.3 and later has a working `tests/browser_smoke.py` for the starter and a CSP that allows the shell's Accessibility score and Tech data requests. In a real app, replace its assertions with the app's own workflow test (keep the file if `tests/browser_security.py` imports helpers from it). An app made from an older template may have the old failing test and a CSP missing `marin-os/data/lighthouse.json` and `marin-os/data/tech.json`; add those two URLs to `security.json` `csp.directives.connect-src`, run `python3 scripts/sync-security-meta.py --write`, and note them in `data.externalDataSources`.
- When an app is served from `localhost`, the shell reads that score and Tech data from a local MarinOS server (`http://localhost:8935`), which the app's CSP blocks on purpose. Ignore that one blocked-request console message in tests and check those two sections on the deployed app.

## Review checklist before accepting generated code

## Boundaries

This skill builds and reviews the *whole* app shell — it doesn't replace a focused review. For a deep pass on one dimension, use the specific skill instead: `accessibility-review` for WCAG conformance beyond this checklist, `design-review` for County visual-identity compliance, `plain-language-review` or `inclusive-language-review` for content, `digital-service-design` for a resident-facing service's task flow, `security-review` for CSP specifics, a genuine security exception, or anything beyond confirming the template's security defaults still fit.

This skill doesn't own project scaffolding or the UI system — those belong to `marin-app-template` and `marin-ui` respectively. If a build repeatedly needs something neither provides, that's a signal to extend the template or `marin-ui`, not to work around the gap inside this skill or a single product.
